# CPU 替代可行性评估（GPU 到位前的本轮范围）

> **状态**：本轮基于本机实测（LENOVO YOGA 14s / Ryzen 7 4800U，8C/16T，16 GB，**无 NVIDIA GPU** /
> torch 2.14.1+cpu / timm 1.0.30 / Python 3.12.13），回答「GPU 到位前能不能用 CPU 顶上」。
> **结论先行**：M0 全部可做且已完成；M2 的**微气象分支可做但不达标**、**视觉分支不可达标**；
> 检测/分割的**全量训练不可做**。详见 §1 表格与 §3 数据。

---

## 1. 结论表：计划中的每个 M2 硬门槛在 CPU 上的可行性

| 计划能力域 | 硬门槛（§1.3） | CPU 可做？ | 实测结果 | 判定 |
|---|---|---|---|---|
| **M0 位置无关底座** | `preflight` 退出 0、单测全绿 | ✅ 完全可做 | 跨盘迁移演练退出码 0；单测 136 项全绿 | **已完成** |
| **M0 SCUT 审计与划分** | 7,296 图一致性 + 双划分 | ✅ 完全可做 | 缺 1 图 / 损坏 52 / 低清 93.2% / 382 终端互斥 | **已完成** |
| **M2 T4 微气象 CatBoost** | Macro-F1 ≥ 0.80 | ⚠️ 可训练，不达标 | **0.334**（Monitor-Holdout） | **不达标** |
| **M2 T4 视觉类型头** | Macro-F1 ≥ 0.80 | ⚠️ 可训练，远不达标 | **0.404**（预训练骨干，160²，8 epoch） | **不达标** |

**一句话**：CPU 能完成 M0 全部、M3 的方法验证部分；M2 的**精度目标**必须等 GPU + 标注。

## 2. 关键发现：微气象分支的 86.7% 是随机帧划分的产物

计划 §3.4.3 引用技术报告表 5-7「纯 3 天微气象 KNN，`P=86.7%`」。本轮用**同一特征、同一模型、
只换划分方式**做对照，结果如下（`artifacts/reports/met_leakage_contrast.json`）：

| 划分方式 | Accuracy | Macro-F1 | 含义 |
|---|---|---|---|
| **随机帧划分** | 0.807 | **0.794** | 同终端图像同时进训练与测试 → 模型背下「该终端常年的气候指纹」 |
| **Monitor-Holdout（计划协议 A）** | 0.533 | **0.334** | 整终端留出 → 必须泛化到**从未见过的新终端** |
| **Temporal-Holdout（2018 留出）** | 0.459 | **0.303** | 跨年份留出 → 更严格 |

> **泄漏虚高幅度 = +0.460 Macro-F1。**

**这不是实现缺陷，而是评估口径问题。** 382 个终端中 179 个跨多年份重复出现且机位固定；
同终端的不同帧共享同一套常年微气候。随机帧划分会把「终端身份」泄漏进特征，让指标看起来
很高。计划 §6.4 已正确识别该风险并要求 Monitor-Holdout，本轮实测**证实了该要求的必要性**——
它把微气象单模态从「看似可用」打到「不可单独使用」。

**对计划的影响（建议）**：
1. §3.4.3 表格中「SCUT 同分布 `P=86.7%`」必须加注「随机帧划分，不可比」——这正是 `AGENTS.md` §3 三栏制要求的「文献值标注不可比」。
2. 微气象分支的定位应从「与视觉并列的融合输入」下调为「弱先验 / 一致性校验」，权重需在 GPU 阶段重新标定。
3. §1.3 中 `T4` 的软目标「视觉+微气象融合 Macro-F1 ≥ 0.88」在微气象单模态仅 0.334 的前提下，需重新论证可达性。

## 4. 视觉类型头为何达不到 0.80（诚实归因）

| 实验 | 骨干 | 输入 | Macro-F1 |
|---|---|---|---|
| 无预训练 | MobileNetV4-Small | 160² | 0.264 |
| **ImageNet 预训练** | MobileNetV4-Small | 160² | **0.404** |

预训练带来 **+0.14** 的提升，证明权重加载正常、训练链路健康。剩余差距的主因按影响排序：

1. **无绝缘子 ROI**（影响最大）：全场图 160² 强缩后，绝缘子串仅剩几十像素；计划 §3.4.3 明确
   「绝缘子 ROI 优先」。而 ROI 需要检测框，检测框需要标注 → **回到 M2 标注瓶颈**。
2. **无 4 类掩码**：计划 §6.5 的 `IceTypeVisualNet` 同时吃图像与掩码特征，本轮只有图像。
3. **分辨率与 epoch 不足**：160² / 8 epoch ≪ 计划 224² / 40 epoch。
4. **任务本身困难**：`glaze↔rime` 混淆 25.9%，低清图下二者纹理差异极小。

**结论**：即使补足 3（更大分辨率 + 更多 epoch），按 1→4 的归因顺序，**不补 ROI 就大概率仍在
0.45–0.55 区间**。这不是算力问题，是**标注问题**。

## 5. 建议的本轮范围（三选一）

### 选项 1（推荐）· 范围收敛为「M0 完成 + M3 方法验证」

- **做**：M0 全部（已完成）；M3 的纯几何算子（`insulator_pa.py`、`baseline_matcher.py`、
  变步长 EKF、`bridge_ratio` 修复）——这些**不需要训练**，CPU 完全够用，且直接对应需求 4。
- **不做**：M2 检测/分割/类型的精度目标，标注为「未验证，待 GPU + 标注」。
- **理由**：M3 是计划中唯一「不依赖大规模训练也能出真结果」的模块，且能立刻消掉
  `pipeline.py:349` 的 `bridge=None` 硬缺陷。GPU 到位后可直接接上 M2。

### 选项 2 · 只做 M0，其余全部等 GPU

- **做**：M0（已完成）。
- **不做**：M1/M2/M3 全部。
- **理由**：最保守，但浪费 CPU 能做的 M3 与 M1 合成算子部分。

### 选项 3 · CPU 硬顶 M2（不推荐）

- **做**：补检测/分割标注后，用 CPU 跑 40 epoch 全量训练（视觉类型头约 1.6 h/次，检测分割数十小时）。
- **风险**：时间长、指标大概率仍不达标、且标注本身需要人工工时（1,500 张掩码复核是本轮最大瓶颈，
  与算力无关）。**不建议**。

| CatBoost 微气象探针 | 特征工程与 NaN 哨兵规则可直接复用 |
