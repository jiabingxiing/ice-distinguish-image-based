# **基于现有标注图像的覆冰类型识别方案（纯 CPU）**

## **一、总体技术结论**

针对 `ice-distinguish-image-based` 项目，我建议采用：

**SCUT 实测图像数据 + 图像质量筛选 + 目标区域裁切 + 预训练轻量级 CNN 特征提取 + SVM 分类 + 少量参数微调 + 置信度拒识。**

第一阶段不建议重新训练大型 YOLO、ViT 或多模态模型，也不建议从零训练 CNN。纯 CPU 条件下，最值得优先尝试的是：

1. 利用现有标注图片训练一个传统机器学习基线，验证不同覆冰类型的纹理和形态是否具有可区分性。
2. 利用 ImageNet 预训练的 MobileNetV3-Small 提取图像特征，冻结主干网络，只训练分类器。
3. 评估效果后，再尝试解冻 CNN 最后一个特征阶段进行少量微调。
4. 对难以区分、质量较差的图片设置拒识机制，而不是强制分类。

这样可以在不使用 GPU 的情况下完成第一版模型，并保留后续迁移到 GPU 或现场监控设备的空间。

这里有一个重要前提：我检查的是 GitHub 中的项目代码、配置和数据说明，并没有直接访问你本地的 SCUT 图像文件。因此，下面能够针对实际数据规模、标注字段和现有代码结构制定方案，但还不能对图片视觉难度和实际分类精度作出结论。

以上视觉特征是用于建立分类判据的初始描述，实际训练前还应结合原始标注规范及图片进行专家复核。

这里需要特别注意两个问题。

**问题一：当前类别配置存在不一致。**

`scripts/build_scut_manifest.py` 已经包含 `wet_snow`，但 `configs/labels/taxonomy.yaml` 中的类别列表是：

```
ice_type:
  labels: [none, glaze, rime, mixed, unknown]
```

并没有 `wet_snow`。

此外，现有实现计划中的 `IcingResult` 类型定义也没有 `wet_snow`。这会造成数据标签、分类输出和接口定义不一致。

建议统一修改为：

```
ice_type:
  labels:
    - glaze
    - rime
    - wet_snow
    - mixed
    - unknown
  reject_policy: confidence_threshold
```

`none` 应作为是否存在覆冰的独立状态处理，不宜直接混入四种覆冰类型的分类任务。

**问题二：不要将少样本类别直接并入 mixed。**

当前 taxonomy 中有一个规则：

```
merge_rule: "单类样本 < 50 时并入 mixed"
```

我不建议保留这个规则。

`mixed` 在物理意义上代表混合覆冰，不代表少样本、难分类或标注不确定。把少数类并入 mixed，会直接污染混合凇的训练标签。

建议：

- 少样本类别仍保留原标签。
- 标注不确定的图片不参与正常监督训练。
- 对没有能力可靠判断的图片输出 `unknown`。
- 某一类别样本确实不足时，先补充标注，不要改变类别物理含义。

## **三、核心模型方案：轻量级迁移学习**

### **3.1 首先明确模型到底学习什么**

本项目应当建立一个独立的覆冰类型分类任务。

输入是一张输电线路监控图片，输出是：

\\[ P(y|I)= \begin{bmatrix} P(\text{glaze})\\\ P(\text{rime})\\\ P(\text{wet\\\_snow})\\\ P(\text{mixed}) \end{bmatrix} \\]

四个概率之和为 1。

这里采用 **Softmax 四分类**，而不是天气识别模块中的多标签 Sigmoid。

两者的区别是：

| 任务     | 输入 | 输出           | 处理方式     |
| ------ | -- | ------------ | -------- |
| 降水天气识别 | 图片 | 雨、雪、雾等可同时存在  | 多标签      |
| 覆冰类型识别 | 图片 | 雨凇、雾凇、湿雪、混合凇 | 四分类      |
| 覆冰存在性  | 图片 | 有冰、无冰        | 二分类      |
| 图片无法判断 | 图片 | 未知、拒识        | 置信度与质量门控 |

本方案只训练第二项。第一项和第三项不作为四分类模型的额外输入。

尤其是 CSV 中已经有的气温、湿度、风速、供电局、终端编号等字段：

- `Ice_Type`：作为训练标签。
- `monitorId`：用于数据分组。
- `Bureau`：用于数据分组和泛化测试。
- `Year`：用于时间测试。
- 气象字段：不输入模型。
- 供电局和终端编号：不输入模型。

这样得到的结果才真正代表**仅凭图像能够达到的覆冰类型识别能力**。

为什么要设计全图和局部两个视角？

因为覆冰类型并不完全取决于颜色。

例如：

- 雨凇需要关注冰壳透明度、反光、致密程度和边缘形态。
- 雾凇需要关注白色不透明区域、粗糙纹理、枝状附着和迎风侧堆积。
- 湿雪需要关注团块形态、表面颗粒和附着特征。
- 混合凇不仅要关注某一处纹理，也需要观察不同覆冰形态在同一设备上的共存。

只看全图，局部冰层纹理可能在缩放时丢失；只看局部，又可能忽略整体覆冰分布。

2026 年发表的 DTL-IceNet 研究也采用了背景、覆冰区域和全图三个分支，研究了局部与全局特征融合对覆冰类型分类的作用。在其独立 IceType 数据集上，完整结构的分类准确率为 95.23%。但该结果不能直接作为本项目的性能预期，其数据集类别、图像分布和训练条件均不相同。

### **3.3 第一阶段：传统图像特征 + SVM**

最先实施

建议先做一个非常轻量的传统机器学习分类器。

目的不是最终部署，而是确认现有图片是否包含可以区分四类覆冰的视觉特征。

提取以下四组特征：

| 特征   | 方法            | 主要识别信息          |
| ---- | ------------- | --------------- |
| 颜色特征 | HSV、RGB 颜色直方图 | 白色、灰白、透明区域的颜色差异 |
| 纹理特征 | LBP           | 表面粗糙度、颗粒和晶体纹理   |
| 方向特征 | HOG           | 冰层轮廓、枝状结构、冰凌方向  |
| 频域特征 | Gabor 滤波      | 不同尺度与方向的纹理变化    |

特征提取后，拼接为一个向量：

\\[ F=[F\_{\text{HSV}},F\_{\text{LBP}}, F\_{\text{HOG}},F\_{\text{Gabor}}] \\]

再使用：

- StandardScaler：特征标准化。
- SVM-RBF：非线性分类。
- `class_weight='balanced'`：缓解类别不均衡。

可以比较两种 SVM：

| 模型         | 特点       | 作用         |
| ---------- | -------- | ---------- |
| Linear SVM | 快、参数少    | 线性基线       |
| RBF SVM    | 能拟合非线性边界 | 主要传统机器学习对照 |

优点是训练速度快，不需要 GPU，不需要预训练权重。

但这种方法有明显局限：不同冰型可能存在较为复杂的空间形态和局部纹理组合，手工特征难以完整表达。

因此，传统特征方案主要用于建立基线，不建议作为唯一技术路线。

### **3.4 第二阶段：MobileNetV3-Small 冻结特征提取**

主推方案

这是我认为最适合当前 CPU 环境的技术方案。

选择 MobileNetV3-Small 的原因：

第一，参数量和计算量较小，适合 CPU 推理。

第二，已经具备 ImageNet 预训练特征，不需要从零开始学习边缘、纹理、形状等基础视觉表示。

第三，项目现有 Python 依赖已经包括 PyTorch 和 torchvision，不需要额外引入大型框架。

第四，分类训练阶段可以完全冻结主干网络，将主要计算转变为一次性特征提取和轻量分类器训练。

PyTorch 官方迁移学习教程也将固定预训练网络作为特征提取器，以及基于预训练权重进行微调，作为小样本图像分类的两种标准迁移学习方式。

| -- | --------------- | ---------- |
| A  | 全图 MobileNet 特征 | Linear SVM |
| B  | 全图 MobileNet 特征 | RBF SVM    |
| C  | 全图 + 覆冰 ROI 特征  | RBF SVM    |

其中 C 是预期优先探索的方案，但不能事先认定一定最好。

**特征提取和分类训练分离。**

这是纯 CPU 条件下很重要的工程技巧。

具体做法：

1. 下载或准备 MobileNetV3-Small 的 ImageNet 预训练权重。
2. 固定所有网络权重。
3. 使用 CPU 将所有图片转换成特征向量。
4. 把特征缓存到磁盘。
5. 使用 scikit-learn 训练 SVM。
6. 保存分类器、标准化器和类别映射。

例如：

```
artifacts/
├── features/
│   ├── scut_train_features.npz
│   ├── scut_val_features.npz
│   └── scut_test_features.npz
│
└── ice_type/
    └── v1/
        ├── mobilenet_v3_small.pth
        ├── svm_classifier.joblib
        ├── scaler.joblib
        ├── temperature.json
        └── model_config.yaml
```

这意味着后续反复调整分类器参数时，不需要重新进行 CNN 前向计算。

例如，可以用同一批 MobileNet 特征比较：

- 线性 SVM。
- RBF SVM。
- Logistic Regression。
- 轻量 MLP。

这些分类器都可以在纯 CPU 环境运行。

### **3.5 第三阶段：只微调网络最后一部分**

只有在第二阶段的验证结果仍有明显改进空间时，才进行微调。

不建议对 MobileNetV3-Small 全部参数进行长时间训练。

推荐配置：

| 参数                     | 建议                |
| ---------------------- | ----------------- |
| Backbone               | MobileNetV3-Small |
| 初始权重                   | ImageNet          |
| 冻结部分                   | 前面所有特征层           |
| 解冻部分                   | 最后 1～2 个特征阶段      |
| 分类头                    | 4 类 Linear Head   |
| 输入分辨率                  | 224，必要时比较 256     |
| Batch Size             | 8                 |
| Head Learning Rate     | 3e-4              |
| Backbone Learning Rate | 1e-5              |
| Epoch                  | 5～10              |
| Optimizer              | AdamW             |
| Weight Decay           | 1e-4              |
| Early Stopping         | 3 个 Epoch 无改善     |

这组参数是首轮实验的起点，不是已经验证的最佳参数。

训练时使用分层学习率：

\\[ L\_{\text{total}}=L\_{\text{CE}}+\lambda L\_{\text{reg}} \\]

其中主要优化目标为四分类交叉熵，分类头学习率高于特征骨干。

训练完成后，与冻结特征方案进行同一测试集对比。

如果微调只提升极少的指标，甚至导致部分类别召回率下降，就保留冻结特征版本，不增加模型复杂度。

## **四、图像预处理：这可能比更换模型更重要**

现有数据 93.2% 的图片宽度不超过 704 像素，大部分为 640×480。

这意味着不需要依靠超高分辨率模型，而需要尽可能保留原有图像中的有效细节。

### **4.1 全图预处理**

统一处理流程：

```
原图
 │
 ├── 解码
 ├── BGR → RGB
 ├── 图像质量检测
 ├── 保持宽高比例
 ├── Resize
 ├── Letterbox Padding
 └── ImageNet Normalize
```

建议初始分辨率：

- 224×224：第一组基线。
- 256×256：主要对照。
- 320×320：仅对局部 ROI 进行效果验证。

不要简单使用强制拉伸，将所有图片直接变成正方形。这会改变绝缘子、导线和冰层的几何形态。

也不建议一开始使用 Real-ESRGAN 等超分辨率方法。生成的高频纹理可能改变本来就不清晰的覆冰细节，产生不真实的判断依据。

### **4.2 覆冰 ROI 裁切**

这是我建议投入一定人工工作的部分。

SCUT 数据有 382 个监测终端，很多监测图片可能具有相对固定的拍摄视角。

因此可以设计：

`monitor_roi_v1.csv`

例如：

```
monitor_id,x1,y1,x2,y2,asset_type
M001,0.32,0.18,0.76,0.82,insulator
M002,0.21,0.25,0.88,0.76,conductor
```

这里坐标使用 0～1 的归一化坐标。

实际执行时：

1. 按照 `monitorId` 统计各监测终端图片。
2. 每个终端选取一张有代表性的图片。
3. 人工框选主要覆冰设备区域。
4. 将 ROI 坐标保存为配置。
5. 同一终端其他图片自动使用对应 ROI。
6. 对视角变化、镜头变焦、设备位置变化的图片增加异常检查。

这样，不需要对 7,000 多张图片逐张框选，只需要针对有价值的监测终端建立 ROI 配置。

如果摄像头并非固定视角，就不能直接复用同一组坐标，需要按摄像头视角版本维护 ROI。

建议分两轮：

**第一轮：** 直接使用全图分类，快速建立基线。

**第二轮：** 增加 ROI，将局部特征与全图特征拼接，验证是否提高 Macro-F1 和少数类别召回率。

尤其是雨凇和雾凇的细节识别，局部区域可能比整张图片缩小后的纹理更加重要。

### **4.3 数据增强策略**

建议只使用不会显著改变覆冰物理含义的增强：

| 增强方式           | 建议                |
| -------------- | ----------------- |
| 亮度调整           | 使用                |
| 对比度调整          | 使用                |
| 轻微色彩调整         | 使用                |
| Gamma 调整       | 使用                |
| JPEG 压缩模拟      | 使用                |
| 小角度旋转          | 谨慎使用              |
| 轻微平移和缩放        | 使用                |
| 水平翻转           | 确认风向及设备方向不构成语义后使用 |
| 垂直翻转           | 不使用               |
| 强烈色彩变换         | 不使用               |
| MixUp / CutMix | 第一阶段不使用           |

特别不建议一开始采用 MixUp。

因为项目本身存在 `mixed` 混合凇类别。把两种冰型的图片人为混合，并不等于真实物理意义上的混合凇，很容易让训练标签和真实覆冰形态产生偏差。

- PyTorch
- torchvision

- 平均单张图片耗时。
- 批量处理耗时。
- CPU 占用率。
- 内存使用量。
- 不同输入尺寸的处理速度。

然后再决定是否调整线程数和 Batch Size。

### **5.3 为什么不建议 CPU 从零训练 CNN？**

假设从随机初始化开始训练 MobileNetV3-Small，就需要通过 7,000 多张图片反复学习：

- 低层边缘。
- 颜色变化。
- 纹理分布。
- 轮廓结构。
- 高层语义信息。
- 四类覆冰的差异。

这会增加训练时间，同时小样本场景下也更容易过拟合。

采用预训练模型后，绝大部分基础视觉特征已经具备。我们的工作主要是利用现有图像重新建立覆冰类型与视觉特征之间的关系。

这正好适合当前没有 GPU 的条件。

### **5.4 模型训练的实际时间如何控制？**

不应直接承诺某个训练时间，因为还不知道当前 CPU 的具体型号、核心数、频率和存储介质。

推荐把训练拆成两部分：

**第一部分：一次性特征提取。**

```
7244 张图片
     │
     ▼
MobileNetV3-Small
     │
     ▼
每张图片生成 576 维特征
     │
     ▼

```

**第二部分：快速分类实验。**

```
  │
  ├── Linear SVM
  ├── RBF SVM
  ├── Logistic Regression
```

这里的分类器实验不再需要重复调用 CNN。

尤其是 RBF SVM、Linear SVM 和 Logistic Regression，非常适合用来快速比较特征的可分性。

## **六、数据划分与模型评价**

这是整个项目能否得到可信结果的关键。

### **6.1 必须以监测终端为单位划分数据**

我建议以当前项目的 Monitor-Holdout 协议作为主评测方案。

仓库已经发现：

- 382 个监测终端。
- 179 个终端存在跨年份重复图像。
- 同一监测终端具有相对固定的背景和拍摄视角。

现有 `scripts/build_scut_manifest.py` 已经设计了按照终端进行分组的主协议，以及按年份划分的时间协议。

### **6.2 类别不均衡处理**

目前 GitHub 只公开了四类标签在各集合中均有覆盖的结论，没有公开每类具体的有效图像数量。需要在本地运行审计脚本获取实际分布。

建议输出：

| 类别  | 总数  | 训练集 | 验证集 | 测试集 |
| --- | --- | --- | --- | --- |
| 雨凇  | 待统计 | 待统计 | 待统计 | 待统计 |
| 雾凇  | 待统计 | 待统计 | 待统计 | 待统计 |
| 湿雪  | 待统计 | 待统计 | 待统计 | 待统计 |
| 混合凇 | 待统计 | 待统计 | 待统计 | 待统计 |

由于不同覆冰类型的样本数量可能存在很大差异，不能只使用总体 Accuracy。

主要评价指标应该是：

\\[ F1\_{\text{macro}}= \frac{1}{4}\sum\_{i=1}^{4} F1_i \\]

同时报告：

- 各类型 Precision。
- 各类型 Recall。
- 各类型 F1。
- Balanced Accuracy。
- 混淆矩阵。
- One-vs-Rest PR-AUC。
- 预测置信度校准情况。

其中最需要检查的是以下混淆：

| 易混淆类别     | 重点分析           |
| --------- | -------------- |
| 雨凇 vs 湿雪  | 反光、透明度、团块形态    |
| 雾凇 vs 混合凇 | 不同类型晶体是否同时出现   |
| 雨凇 vs 混合凇 | 致密冰壳是否伴随其他附着形态 |
| 雾凇 vs 湿雪  | 晶体结构与松散积附结构    |

如果某一类明显少于其他类，优先使用类别权重和适度的训练集过采样，而不是先生成大量人工合成图片。

### **6.3 必须增加模型拒识能力**

电网防灾业务中，错误地把雨凇判断为雾凇，可能影响后续风险研判。

所以不能要求模型每张图片都必须输出四分类之一。

建议：

\\[ \hat y = \begin{cases} \text{unknown}, & q\_{\text{image}} < \tau_q\\\ \text{unknown}, & \max_i p_i < \tau_p\\\ \arg\max_i p_i, & \text{其他} \end{cases} \\]

其中：

- \\(q\_{\text{image}}\\)：图片质量评价。
- \\(\tau_q\\)：质量阈值。
- \\(p_i\\)：四类覆冰的预测概率。
- \\(\tau_p\\)：分类拒识阈值。

阈值通过验证集确定，而不是直接写死。

建议再加入 Top-1 与 Top-2 概率差值检查。例如模型判断：

```
雨凇：0.46
混合凇：0.43
雾凇：0.07
湿雪：0.04
```

即使雨凇是最高概率，也不应该直接视为可信的自动判断结果。

对低置信度样本输出：

```
{
  "ice_type": "unknown",
  "requires_review": true,
  "reason": "ambiguous_prediction"
}
```

这样可以避免模型对本身无法判断的图像作出过于确定的结论。

## **八、部署方案：CPU 推理**

训练结束后，不建议生产服务直接加载完整训练环境。

推荐流程：

```
PyTorch 训练模型
       │
       ▼
导出 ONNX FP32
       │
       ▼
ONNX Runtime
       │
       ▼
CPUExecutionProvider
       │
       ▼
图像分类服务
       │
       ▼
统一 IcingResult
```

使用 ONNX Runtime 时，可以设置：

```
import onnxruntime as ortoptions = ort.SessionOptions()options.intra_op_num_threads = 8options.inter_op_num_threads = 1options.graph_optimization_level = (    ort.GraphOptimizationLevel.ORT_ENABLE_ALL)session = ort.InferenceSession(    "ice_type.onnx",    sess_options=options,    providers=["CPUExecutionProvider"])
```

线程数需要根据实际处理器测试，不一定 8 线程就是最佳配置。ONNX Runtime 官方提供了算子内并行、算子间并行和线程池调优机制。

## **九、需要关注的研究和技术参考**

这里有三个与项目直接相关的研究方向。

**1. 基于南方电网监控图像的弱监督迁移学习**

2022 年 IET Generation, Transmission & Distribution 发表了《Methods of image recognition of overhead power line insulators and ice types based on deep weakly-supervised and transfer learning》。

该研究使用南方电网 2014—2018 年监控图像，236,000 张原始图片经过清洗后有约 197,000 张可用于分析，其中包含约 14,000 张覆冰绝缘子图片，并指出不同覆冰类型存在明显样本不均衡。

其方法采用分阶段迁移学习，研究了正常、雪、雾凇、混合凇和雨凇识别。

[image](https://www.google.com/s2/favicons?domain=https://ietresearch.onlinelibrary.wiley.com\&sz=32)

Wiley Online Library+1



这项研究对本项目最有价值的地方不是直接复现 YOLOv5，而是：

- 迁移学习比从零训练更有优势。
- 设备定位和覆冰类型识别需要关注不同层级的特征。
- 样本不均衡必须纳入训练和评价。
- 不能单纯利用整张图片的背景信息。

**2. DTL-IceNet：局部覆冰与全局环境特征融合**

2026 年发表的 DTL-IceNet 研究构建了 20,684 张冰型识别图片，并使用背景分支、覆冰分支和全局分支提取互补特征。

其结果说明，全图信息和局部冰层信息具有互补性。

[image](https://www.google.com/s2/favicons?domain=https://amt.copernicus.org\&sz=32)

AMT+1



因此，我建议本项目采用轻量化的双视角架构，而不是单纯将图片缩小后输入 CNN。

注意：该研究数据集与本项目类别定义不同，而且项目现有数据许可台账将 DTL-IceNet 标记为授权待确认，不建议未经授权直接将其图像用于训练。

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

GitHub



**3. 微气象数据融合与图像识别**

2026 年《南方电网技术》相关研究使用三天微气象时间序列与监控图像融合，利用 GSM-XGBoost 取得了 95.6% 的 Macro-F1。

[image](https://www.google.com/s2/favicons?domain=https://nfdwjs.csg.cn\&sz=32)

nfdwjs.csg.cn

本阶段仍然坚持图像单模态，把微气象数据留作后续独立对照实验。

### **10.1 最终验收应该关注什么？**

第一轮不要预先要求达到 95% 或 98% 准确率。

建议设置三组评价条件：

| 评价维度  | 验收内容                        |
| ----- | --------------------------- |
| 数据可靠性 | 损坏图像剔除、标签映射正确、无重复泄漏         |
| 分类能力  | 四类 Macro-F1、各类别 Recall、混淆矩阵 |
| 工程能力  | CPU 推理、拒识、模型复现、接口一致性        |

在第一轮得到真实基线之后，再制定 Macro-F1 和各类别 Recall 的正式验收目标。

模型不仅要看总体成绩，还必须检查不同供电局、不同监测终端和不同年份的数据表现。

## **十一、最终建议：先实现三个模型，不要急于复杂化**

我的实际建议是，项目第一个版本只需要实现以下三种模型：

| 优先级 | 模型                                 | 是否需要 GPU | 主要目的      |
| --- | ---------------------------------- | -------- | --------- |
| P0  | HOG + LBP + SVM                    | 不需要      | 传统特征基线    |
| P1  | MobileNetV3-Small + 冻结特征 + SVM     | 不需要      | 主力图像分类模型  |
| P2  | MobileNetV3-Small + 局部/全图特征 + 末端微调 | 不需要      | 提升细粒度识别能力 |

暂时不推荐：

- YOLOv8/YOLO11：目前没有必要为了四分类额外引入完整检测训练任务。
- U-Net：当前没有足够的冰层像素掩码需求来支撑这个分类任务。
- EfficientNet-B3：纯 CPU 环境下没有必要首先尝试更重的模型。
- ViT/DINO 大模型：计算量和部署复杂度暂时不值得。
- 从零训练 CNN：没有必要放弃 ImageNet 预训练特征。

**我最推荐的实际实施路线是：先用 MobileNetV3-Small 冻结特征提取，配合 RBF SVM 完成四类覆冰分类，再通过监测终端 ROI 裁切解决背景干扰。**

这条路线不依赖 GPU，也不需要重新制作数千张图片的人工标注。对于现有约 7,200 张标注图像，具备实际执行条件。

另外，整个方案有一个必须坚持的原则：模型要学习的是雨凇、雾凇、湿雪和混合凇本身的视觉差异，而不是通过监测终端背景、年份或气象字段间接猜测类别。

**建议接下来优先开展 P0：针对 SCUT 的 7,244 张有效图片输出四类覆冰的真实数量、每类随机抽样图片集、尺寸分布和终端分布。** 这一步的数据报告将直接决定后续模型应该使用全图、局部 ROI，还是双视角分类。
